# 03 七个数据缺陷复盘

**这是本项目最有价值的部分。**

七个缺陷全部是**静默失败**：不崩溃、不报错、不写日志，
只是产生一个"合法但错误"的数字，然后被后续所有分析当作事实使用。

| # | 缺陷 | 静默方式 | 漏检量级 |
|---|---|---|---|
| 1 | `find_soi` 抽样扫描 | 少找到起始标记 | **93.5%** |
| 2 | `probe` 只读前 4 MB | 结束标记在远处即判失败 | 未知（静默丢弃） |
| 3 | `int` 与 `bytes` 比较 | 条件恒为真，函数直接返回 | **100%** |
| 4 | 读 4 字节却访问第 5 字节 | `IndexError` 被上层 `except` 吞掉 | **100%** |
| 5 | PNG 尺寸多读 4 字节 | 读出合法但错误的宽高 | 7,917 条 |
| 6 | HEIC 取第一个 `ispe` | 返回合法但错误的尺寸 | **97.6%** |
| 7 | README 摘要未同步 | 文档与数据不一致 | 说明失真 |

---

## 缺陷 1：抽样扫描漏掉 93.5% 的起始标记

```python
# 错误：跳跃采样
o += step          # 跳过中间区域
```

实测某个 1.5 GB 容器：
- 抽样扫描 → **123** 个 JPEG 起始标记
- 连续扫描 → **1,890** 个

**漏检 93.5%**。原因是真实标记集中在 3.7 MB 之后，恰好落在采样盲区。

**修复**：连续扫描 + 保留 2 字节跨块边界缓冲。

**教训**：对二进制容器做内容发现，**采样永远不能代替全扫**。

---

## 缺陷 2：只读前 4 MB 就判定失败

```python
b = f.read(min(4_000_000, size - off))
e = b.find(b"\xff\xd9")
if e < 0: return None      # 结束标记在 4 MB 外 → 静默丢弃
```

大 JPEG 的结束标记可能在几十 MB 之外，被当作"没有结束标记"丢弃，
且**不产生任何记录**。

**修复**：分块流式查找，上限 200 MB，块间保留 1 字节防止标记跨块漏检。

---

## 缺陷 3：`int` 与 `bytes` 比较，条件恒为真（最隐蔽）

```python
if len(head) < 3 or head[:2] != b"\xff\xd8" or head[2] != b"\xff":
    return None
```

`head[2]` 是 **int**（值为 255），`b"\xff"` 是 **bytes**（长度 1）。

```
255 != b"\xff"   →  True （永远是 True）
```

**所有调用直接返回 `None`。**

表现形式极具迷惑性：

```
起始标记 = 1,890   （完全正确）
结束标记 = 0       （全部丢失）
导出     = 0
```

看起来像"这些数据确实没有完整 JPEG"，实际是类型比较错误。

**修复**：`head[2] != 0xFF`。

**教训**：Python 里 `int` 和 `bytes` 比较**不报错**，只是永远不相等。
凡是拿 `bytes` 索引结果和 `b"..."` 比较的地方，都应视为高风险代码。

## 缺陷 4：读 4 字节却访问第 5、第 6 字节

```python
head = f.read(4)
...
seg_len = (head[4] << 8) | head[5]   # IndexError
```

`IndexError` 被上层宽泛的 `except` 捕获，当作"解码失败"处理，
于是**整个分支静默返回 `None`**，没有任何日志。

**修复**：`head = f.read(6)`（起始标记 2 + 段类型 1 + 段长 2 = 至少 6 字节）。

**教训**：宽泛的 `except` 会把编码错误伪装成数据问题。
解析二进制时，`IndexError` 必须显式处理，不能归入"解码失败"。

## 缺陷 5：PNG 尺寸解析多读 4 字节

PNG 的 `IHDR` 结构：

```
[8 字节签名][4 字节块长][4 字节块类型][4 字节宽][4 字节高]...
```

错误实现：

```python
fh.read(8)                    # 签名
fh.read(4); t = fh.read(4)    # 块长、块类型
fh.read(4)                    # ← 多读 4 字节，把"宽"跳过了
w, h = struct.unpack(">II", fh.read(8))
```

结果：
- `w` 读到真实**高**
- `h` 读到 `IHDR` 的位深/颜色类型字节

对于 8 位 RGB PNG，这 4 字节是 `08 02 00 00`，按大端解释 = **134,348,800**。

这就是那个反复出现、看起来"像哨兵值"的数字的**真正来源**。

### 实测证据

```
文件：某长截图
  exiftool 报告 : 1248 x 19494
  错误实现      : 19494 x 134348800   （261.9 万像素 → 2.6 亿像素）
  修正后        : 1248 x 19494        ✓
```

### 影响

- 50,582 条记录中 **7,917 条**尺寸错误
- 高清清单的 PNG 部分**完全不可信**
- 长截图被误判为超大图，进而被像素上限跳过

## 缺陷 6：HEIC 取第一个 `ispe`（影响最大）

HEIC 是 ISO BMFF 容器，**一个文件里有多个 `ispe`（空间范围）box**：

```
某 HEIC 文件：
  ispe @2,314 : 512 x 512      ← 缩略图/预视图
  ispe @2,334 : 4032 x 3024    ← 主图（正确尺寸）
  ispe @2,379 : 320 x 240      ← 更小的缩略图
  ispe @2,399 : 2016 x 1512    ← 中间尺寸
```

错误实现遇到第一个合法 `ispe` 就 `return`，拿到 `512×512`。

### 全量实测（16,863 个 HEIC，不是抽样）

```json
{
  "files": 16863,
  "resolved": 16828,
  "multi_ispe": 16454,
  "first_would_differ": 16454
}
```

**97.6% 的文件有多个 `ispe`，且第一个不是主图。**

### 影响

| 项 | 修复前 | 修复后 | 差值 |
|---|---:|---:|---:|
| HEIC 高清数 | **389** | **16,758** | **+16,369** |
| 高清清单总数 | 32,303 | **48,672** | +16,369 |
| 高清总字节 | 87.7 GB | 116.4 GB | +28.7 GB |

**HEIC 从占比 1.2% 变成 34.4%，是第二大来源。**

### 为什么这个缺陷特别危险

| 特性 | 说明 |
|---|---|
| 静默 | 无报错，只是尺寸读小了 |
| 自洽 | `512×512` 是合法尺寸，通过所有合理性检查 |
| 一致 | 97.6% 的文件都这样，看起来"正常" |
| 误导 | 让 HEIC 在统计中显得只占 1.2% |
| 外推错误 | 按 444 条样本推得 215 条（2%），实际是 97.6% |

### 修复

取**面积最大**的 `ispe`，而不是第一个：

```python
cands = []
i = data.find(b"ispe")
while i > 0 and i < len(data) - 20:
    w, h = struct.unpack(">II", data[i+8:i+16])
    if 0 < w < 30000 and 0 < h < 30000:
        cands.append((w, h))
    i = data.find(b"ispe", i + 4)
best = max(cands, key=lambda t: t[0] * t[1])
```

### 验证

修复后抽检已索引对象：

```json
{"w": 240, "h": 320, "real_w": 3024, "real_h": 4032, "ok": true}
```

`real_w/real_h` = 3024×4032 与 `exiftool` 一致；`w/h` = 240×320 是哈希用的缩略尺寸。
2,532 个已索引 HEIC 中，`real` 仍为 `512×512` 的数量：**0**。

## 缺陷 7：文档摘要与数据不同步

交付包里的 README 摘要仍写着旧的记录池数量，
而实际被检索的参考清单是另一个数字。

**教训**：交付物的**机器数据**和**人类可读摘要**必须同时生成并交叉校验。
只校验 JSONL 而不校验 README 是不够的。

## 共同模式与工程建议

七个缺陷里有 **5 个**属于同一类：
**"合法性检查通过 ≠ 正确"**。

| 检查 | 能通过什么 | 挡不住什么 |
|---|---|---|
| 尺寸 > 0 | 512×512 缩略图 | 主图被漏选 |
| 文件头签名匹配 | `ffd8ffe0` | 后面跟随机字节 |
| 解码成功（宽松解码器） | 结构性损坏 | 内容错误 |

### 建议

1. **二进制解析必须有独立来源交叉验证**
   尺寸用两种方法（文件头 + EXIF），不一致就报警而不是静默取一个。

2. **禁止宽松的 `except`**
   把 `IndexError`/`TypeError` 和"数据损坏"分开处理，前者必须尖叫。

3. **`bytes` 索引用常量比较**
   `head[2] != 0xFF`，不要写 `head[2] != b"\xff"`。
   建议加静态检查规则。

4. **抽样只用于估算，不用于结论**
   任何"漏检率""占比"结论必须来自全量扫描。

5. **交付物摘要与数据同步生成**
   摘要里的每个数字都应能在机器数据里定位到对应字段。

6. **恒等式必须显式写出并校验**
   例如 `导出 + 跳过 = 完整流`、`唯一 + 折叠 = 导出`。
   本次审计中，恒等式校验是发现缺陷 1 和 5 的直接手段。
