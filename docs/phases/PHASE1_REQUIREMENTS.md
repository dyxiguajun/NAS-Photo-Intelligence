# NAS Photo Intelligence Engine — Phase 1 开发交接指令

## 一、项目背景与当前状态

你将继续开发一个长期项目：

**NAS Photo Intelligence Engine（NAS 照片智能分析与整理引擎）**

该项目旨在分析分散于 NAS 不同目录中的照片、视频和历史备份，建立统一索引，为未来的智能去重、相似照片识别、元数据修复建议和照片整理提供基础。

用户的 NAS 保存了来自多个设备和历史阶段的照片，包括：

- 智能手机自动备份
- 历史设备照片
- 数据恢复软件恢复的文件
- OneDrive 同步文件
- 多次迁移产生的重复备份
- 照片及 Live Photo 配套视频
- 可能经过编辑、压缩或重新编码的照片

其中，部分文件在历史硬盘故障、数据恢复或迁移过程中丢失了元数据，或出现明显异常的文件系统时间。

项目最终希望解决的不仅是完全相同文件的去重问题，还包括：

1. 内容相同但文件格式不同的照片。
2. 内容相同但分辨率不同的照片。
3. 原始照片与经过编辑、压缩的版本。
4. 图像内容相同但元数据完整度不同的版本。
5. 文件系统时间异常，但内部拍摄时间仍然正常的照片。
6. EXIF 缺失，需要利用其他证据推断拍摄时间的照片。
7. 不同设备、不同备份来源之间重复的照片。
8. Live Photo、视频及其关联资源。

最终目标是构建一个**保留原始证据、支持智能分析、可解释且能够由用户审核的照片管理系统**。

但本次只执行 Phase 1，不提前开发后续阶段。

## 三、当前网络环境已经变化

用户目前不在公寓。

MacBook 通过 Tailscale 远程访问 NAS。

当前提供的 NAS Tailscale 地址为：

`<TAILSCALE_NAS_IP>`

此前 NAS 的公寓局域网地址为：

`<LAN_NAS_IP>`

这两个地址指向同一台 NAS，不应被当成不同设备。

### 首先检查远程连接

请使用现有工具验证：

1. Tailscale 网络连接状态。
2. NAS Tailscale 地址的可达性。
3. SMB 445 端口连通性。
4. 当前是否已经存在有效的 SMB 挂载。
5. 现有挂载是否可以实际读取照片文件。

可以采用适当的工具，例如：

```bash
tailscale ping <TAILSCALE_NAS_IP>
```

以及：

```bash
nc -G 5 -vz <TAILSCALE_NAS_IP> 445
```

具体检查方式可以根据实际环境调整。

注意：

- 不要默认原来的局域网 IP 仍然可以访问。
- 不要仅凭端口开放就判断 SMB 文件读取正常。
- 如果现有挂载正常，优先复用。
- 如果挂载已经失效，诊断后再决定是否重新连接。
- 不要创建多个不必要的重复挂载。
- 不要随意修改 NAS 网络设置。
- 不要重新创建 NAS 用户。
- 不要修改共享权限。
- 不要主动更换已有的认证方案。

此前 NAS SSH 端口可达，但严格主机密钥验证未通过。

这不等于 SSH 账号或密码错误。

不得通过关闭 SSH 主机身份验证来绕过该问题。

Phase 1 不以获得 NAS SSH 管理权限作为前提。

### 重要架构要求

**照片来源的逻辑身份必须与网络地址、SMB 挂载路径分离。**

例如：

同一个照片目录通过公寓局域网访问，或者通过 Tailscale 访问，其来源 ID 应保持一致。

建议采用：

- 稳定的 NAS 设备标识。
- 稳定的 source_id。
- 来源内部相对路径。
- 可变的挂载根路径。

避免因为挂载名称变化、IP 地址变化，导致数据库认为全部照片都是新文件。

## 五、照片元数据与异常时间识别

这是本次开发中需要特别重视的部分。

### 1. 修正此前关于 1970 年的描述

用户历史数据恢复过程中遇到的文件时间异常，**并不一定精确发生在 1970 年**。

实际可能出现：

- 1969～1970 年附近。
- 1980 年代。
- 1990 年代。
- 2000 年以前的其他日期。
- 明显晚于真实拍摄时间的日期。
- 超出有效日期范围的时间。
- 时间字段溢出。
- 文件系统时间与 EXIF 严重冲突。
- 文件创建时间与修改时间互相矛盾。

因此：

**不要只检测 Unix Epoch 或 1970 年。**

建议将：

`2000-01-01 00:00:00`

作为默认的早期文件系统时间异常筛查阈值。

但要注意：

**该阈值只能用于标记可疑情况，不能直接证明照片时间错误。**

2000 年以前完全可能存在真实拍摄的照片。

另外，2000 年以后的时间也可能是错误的。

这一阈值必须可配置，不应硬编码成照片的绝对有效日期下限。

### 2. 元数据采集要求

尽可能保存：

**文件系统信息**

- 文件名。
- 扩展名。
- 文件大小。
- 创建时间。
- 修改时间。
- 时间字段原始数值。
- 来源 ID。
- 相对路径。

**照片内部信息**

- EXIF DateTimeOriginal。
- EXIF DateTimeDigitized。
- EXIF ModifyDate。
- 时区偏移。
- 相机品牌。
- 相机型号。
- 镜头信息。
- 图像尺寸。
- 图像方向。
- 文件内部格式。
- 其他可合理提取的时间证据。

**其他辅助证据**

- 文件名包含的日期。
- 来源目录中的日期。
- 视频容器中的创建时间。
- 不同元数据工具的识别结果。
- 可能存在的关联资源信息。

对于无法解析的超大时间值、溢出值，不得让程序崩溃。

可以保存原始字符串及错误标记。

不要强制将所有时间转换为 Unix 时间戳。

对于没有明确时区的日期，应保留其时区未知状态，不能擅自当成 UTC。

### 3. 异常标签设计

建议至少支持：

`early_filesystem_timestamp`

文件系统时间早于配置的筛查阈值。

`invalid_timestamp`

时间数值无效、溢出或无法解析。

`missing_capture_time`

缺少可靠的拍摄时间信息。

`timestamp_conflict`

多个时间证据存在明显冲突。

`timezone_uncertain`

时间缺少必要的时区信息。

`future_timestamp`

日期明显超出合理的未来范围。

`metadata_incomplete`

部分重要元数据缺失。

`format_identification_conflict`

不同工具对真实文件格式的判断不一致。

这些标签应保存于数据库，并允许后续修改或重新计算。

### 4. 不要简单采用时间优先级

例如：

照片 A：

- 文件创建时间：1985 年。
- EXIF 拍摄时间：2023 年。
- 相机型号：现代智能手机。

这种情况可以标记为文件系统时间疑似异常。

但如果照片 B：

- 文件创建时间：1998 年。
- EXIF 拍摄时间：1998 年。
- 相机型号：历史设备。

就不能因为时间早于 2000 年而直接认定为错误。

此外：

照片 C：

- 文件修改时间：2024 年。
- EXIF 拍摄时间：2021 年。

也可能只是经历了文件复制、下载、同步或重新编码。

因此：

**不要默认日期越新越可靠，也不要默认 EXIF 一定正确。**

Phase 1 的任务是保存证据、发现异常，而不是武断地确定唯一正确时间。

复杂的时间可信度评分，可以留待后续阶段。

## 六、元数据完整度与时间可靠性必须分开

这一点关系到未来的智能去重功能。

请避免只设计一个简单的“照片质量分数”。

至少区分以下维度：

**内容质量**

例如：

- 分辨率。
- 文件完整性。
- 编码格式。
- 有损压缩情况。

**元数据完整度**

例如：

- 是否保留拍摄时间。
- 是否保留相机型号。
- 是否保留镜头信息。
- 是否包含 GPS 元数据。
- 是否保留其他原始信息。

**时间可靠性**

例如：

- 时间来源是否明确。
- 是否存在字段冲突。
- 是否缺少时区。
- 是否明显不符合设备年代。

**来源可信度**

例如：

- 原始手机备份。
- 云端同步目录。
- 历史迁移目录。
- 数据恢复目录。

来源可以作为参考证据，但不能仅根据目录名称赋予绝对可信度。

Phase 0 已发现：

同一个恢复目录中，有些照片丢失 EXIF，有些却保留了完整内部时间。

因此不得简单规定：

“恢复目录的照片元数据一定不可靠。”

本阶段只需要为以上维度建立合理的数据结构。

**不要求立即开发复杂评分模型。**

## 七、数据库与工程架构

建议优先采用 Python + SQLite。

可以根据实际需求选择成熟的第三方库。

但不要求使用某个指定框架。

### 数据库设计

应能够保存：

- 来源配置。
- 文件基本信息。
- 文件系统时间。
- 元数据原始值。
- 解析后的元数据。
- 异常标签。
- 文件扫描状态。
- 错误信息。
- 扫描任务进度。
- 后续分析所需的关联字段。

数据库应支持未来扩展，例如：

- SHA-256。
- 感知哈希。
- 视觉相似度。
- 文件版本关系。
- 元数据可信度分析。
- 用户审核状态。
- 建议保留版本。
- 待删除候选。

但 Phase 1 不需要提前实现上述算法。

### 存储位置

本阶段数据库应保存在 Mac 本地。

不要直接通过 SMB 在 NAS 上运行 SQLite WAL 数据库。

建议将：

- 数据库。
- 日志。
- 缓存。
- 配置。
- 测试报告。

分别存放于项目的独立目录。

原始照片目录只能作为输入来源。

不要在 NAS 原始照片目录中写入索引文件。

## 八、远程网络环境下的扫描可靠性

当前 Mac 通过 Tailscale 远程连接 NAS。

因此必须考虑：

- 网络延迟。
- 带宽变化。
- SMB 连接中断。
- 挂载失效。
- 单个文件读取缓慢。
- 文件突然不可访问。
- Work 任务被中断。
- Mac 重启。
- 执行额度不足。

### 核心要求

扫描程序应支持：

1. 持久化扫描状态。
2. 已完成文件记录。
3. 失败文件记录。
4. 有限次数重试。
5. 合理超时机制。
6. 安全取消。
7. 中断后恢复。
8. 增量扫描。
9. 有限内存占用。
10. 结构化错误日志。

不要采用简单的：

扫描全部文件 → 保存最终结果

这种容易丢失进度的方案。

建议采用分批处理和数据库事务。

已经成功完成的批次应尽可能保留。

### 性能要求

MacBook Air 只有 8GB RAM。

因此：

- 不要将大量照片一次性读入内存。
- 不要默认高并发。
- 不要为索引创建大量原图副本。
- 优先读取元数据。
- 必要时按需读取文件内容。
- 避免无意义地重复扫描。
- 不要对全部照片进行图像解码。

对于远程 NAS，避免未经测试就使用大量并行 SMB 请求。

可以设计可配置的并发与批次参数。

## 九、图片与视频格式支持

优先支持：

- JPEG
- PNG
- HEIC
- MOV

根据实际发现的文件，可以逐步支持：

- WebP
- JFIF
- MP4
- TIFF
- 其他常见照片格式

对于无法解析的格式，应记录错误，不得影响其他文件。

特别注意：

Phase 0 曾发现部分 JPEG 文件被 macOS ImageIO 返回为 HEIC 类型。

后续通过文件头及其他工具交叉核验，确认这些文件实际为 JPEG。

因此：

**不能仅根据扩展名判断真实格式，也不能仅根据某个工具的单次识别结果认定文件格式。**

对于识别冲突，应保存证据。

另外，Live Photo 可能包含：

- HEIC/JPEG 主图。
- MOV 配套视频。

不能因为文件名相同或拍摄时间接近，就直接认定它们完全重复。

未来需要保留关联关系。

Phase 1 可以先记录候选关联，暂不执行复杂的 Live Photo 配对算法。

- 自动修复 EXIF。
- 修改照片时间。
- 修改 NAS 文件权限。
- 上传原始照片到外部 AI 服务。

## 十四、Phase 1 验收标准

本阶段结束时，不应该只有设计方案。

应尽可能实际交付：

### 1. 可运行程序

能够从指定来源读取照片信息，并建立 SQLite 索引。

### 2. 数据库

能够保存来源、文件身份、元数据、异常标签、扫描状态及错误信息。

### 3. 时间异常识别

能够识别：

- 2000 年以前的可疑文件系统时间。
- 无效或溢出的时间。
- 缺失的拍摄时间。
- 明显冲突的时间。
- 未知时区。
- 异常未来日期。

同时不会将所有 2000 年以前的照片判定为错误。

### 4. 扫描与恢复

程序可以在有限样本范围内正常扫描，并通过实际测试或可复现的故障注入证明断点恢复能力。

### 5. 增量能力

重复运行时，不会无条件重新建立全部记录。

同一 NAS 通过不同挂载路径访问时，不会因为路径变化自动产生重复来源。

### 6. 数据安全

所有真实 NAS 照片保持原样。

只允许读取，不允许修改。

### 7. 测试报告

明确记录：

- 实际处理文件数量。
- 成功数量。
- 失败数量。
- 异常类型及数量。
- 测试耗时。
- 数据库大小。
- 实际验证的功能。
- 尚未验证的功能。

不要虚构测试结果。

### 8. 工程文档

提供：

- 项目结构说明。
- 运行方法。
- 配置说明。
- 数据库结构说明。
- 测试方法。
- 故障恢复方式。

### 我的补充判断

这次交接还有一个很重要的工程方向：**索引应该能够长期复用，而不是随着网络连接和存储位置变化不断重建。**

你现在通过 Tailscale 访问 NAS，以后回到公寓又会使用局域网。如果系统把完整的 SMB 挂载路径当作照片唯一身份，未来很容易出现重复索引。

另外，对于时间异常，我认为这次修改是必要的。Phase 0 实际发现了接近 Unix 纪元的时间，以及超出正常日期范围的 SMB 创建时间。PHASE0_REPORT 但这只能证明部分样本存在这些问题，不能代表整个照片库的异常日期都集中在 1970 年。

**最终策略应该是：以 2000 年作为初步筛查线，用多来源证据判断时间可信度，保留无法确定的情况，而不是强行修正。**

还有一点：我建议继续让 **Mac 负责 Phase 1 的开发和有限测试，NAS 暂时只作为只读数据源**。这样能够绕开尚未解决的 NAS SSH、Docker 部署问题，减少远程开发过程中的额外工作量。
