# 四、Phase 3 的核心目标

本阶段重点解决：

**不同文件是否可能来自同一张照片或同一视觉内容。**

必须明确区分三个概念。

### 第一类：二进制完全相同

两个文件的完整 SHA-256 一致。

这已经是 Phase 2 的能力。

Phase 3 应直接复用，不重新造轮子。

### 第二类：解码后的图像像素相同

例如：

两张 PNG 图片的像素完全一致，但其中一张包含额外元数据。

两张文件可能拥有不同 SHA-256，但解码后的像素内容完全相同。

Phase 3 应能够识别这种关系。

### 第三类：视觉相似

例如：

- 同一张照片经过 JPEG 重新压缩。
- 同一张照片从 HEIC 转换为 JPEG。
- 同一张照片被缩放。
- 同一张照片被旋转。
- 同一张照片发生轻微颜色变化。
- 同一张照片存在不同程度的裁剪。

这些文件通常不会拥有相同的完整 SHA-256。

解码后的像素也可能不同。

因此需要感知哈希等视觉分析方法。

### 本阶段的目标层次

| 层次 | 目标 | 本轮要求 |
|---|---|---|
| L0 | 二进制完全相同 | 复用 Phase 2 |
| L1 | 规范化后像素完全相同 | 必须实现 |
| L2 | 视觉近似 | 必须实现基础能力 |
| L3 | 大幅裁剪、复杂编辑后的语义相似 | 评估可行性，不强制实现 |

**Phase 3 必须完成 L1、L2 的可靠基础能力。**

不要为了追求复杂效果而提前引入大型视觉模型。

# 六、L1：像素级相同检测

本阶段首先实现规范化图像的像素比较。

### 核心目标

识别：

**文件字节不同，但经过明确、可复现的解码和规范化后，图像像素完全一致的文件。**

例如：

```text
A.png
SHA-256: abc...

B.png
SHA-256: def...

图像尺寸：
1920 × 1080

规范化后的像素：
完全相同

结论：
L1 图像内容一致
```

### 建议流程

1. 读取图片。
2. 检查真实文件格式。
3. 解码图像。
4. 根据规则处理 EXIF Orientation。
5. 统一明确的像素格式。
6. 按选定策略处理颜色模式和色彩空间。
7. 记录宽高。
8. 对规范化后的完整像素数据计算哈希。
9. 保存规范化规则版本。
10. 根据有效结果建立 L1 相同关系。

可考虑使用 SHA-256 计算规范化后的像素指纹。

但必须区别：

`file_sha256`

和：

`pixel_sha256`

两者不能混淆。

### 规范化要求

建议至少记录：

- 图像尺寸。
- EXIF Orientation。
- 实际使用的方向修正。
- 解码器名称与版本。
- 色彩空间处理策略。
- Alpha 通道处理策略。
- 像素格式。
- 规范化算法版本。

尤其注意：

**不同色彩管理方式可能导致解码后的像素值不同。**

不要在未定义规范化规则的情况下，直接宣称所有设备上的像素哈希完全可互换。

建议把 L1 定义为：

> 在指定算法版本、解码器及规范化规则下，输出的图像像素完全一致。

这比笼统声称“原始画面绝对相同”更加准确。

### 文件尺寸限制

完整图像解码可能消耗大量内存。

应支持：

- 最大允许图像尺寸。
- 最大解码像素数。
- 单文件解码内存保护。
- 超时处理。
- 格式异常处理。

对于超大照片，不能为了生成完整像素哈希而导致 Mac 内存耗尽。

如果超过资源限制，允许跳过 L1，但应记录原因。

不能将“未分析”当作“不相同”。

# 七、L2：视觉相似检测

这一层是本阶段的重点。

主要目标：

**识别经过压缩、缩放、编码转换或轻微编辑后的同源照片候选。**

建议首先评估：

- pHash。
- dHash。
- aHash。
- 其他成熟的轻量感知指纹。

不要求全部实现。

可以选择一种主算法，必要时配合另一种算法进行辅助判断。

### 7.1 感知哈希

例如：

```text
原图：
IMG_1234.HEIC

转换版本：
IMG_1234.jpg

两个文件 SHA-256 不同。

规范化像素不同。

但感知哈希距离较小。

系统标记：
视觉相似候选。
```

对于感知哈希，需要保存：

- 算法名称。
- 算法版本。
- 哈希长度。
- 哈希值。
- 预处理参数。
- 距离计算方法。
- 阈值。
- 解码器信息。

不能只存储一个没有说明来源的整数。

### 7.2 相似度判断

感知哈希通常可以使用汉明距离比较。

但必须注意：

**距离小不代表两张图片一定来自同一张照片。**

例如：

- 纯色图片。
- 大面积天空。
- 相似的建筑。
- 连拍照片。
- 相似构图。
- 同一个场景不同时间拍摄。

都可能得到比较接近的指纹。

因此：

感知哈希结果应首先形成候选关系。

不应直接生成删除建议。

### 7.3 阈值策略

相似度阈值必须可配置。

可以设计：

- 高相似候选。
- 一般相似候选。
- 低置信度候选。

但这些等级必须有明确算法依据。

不要凭空生成类似：

`98.7% 相同概率`

这样的数值。

除非经过实际数据校准，否则不要把感知哈希距离转换成统计概率。

可以直接输出：

```text
算法：pHash
距离：4
哈希长度：64 bit
判定：达到当前高相似候选阈值
```

这种方式更可解释。

### 7.4 二次验证

对于感知哈希非常接近的候选，可以考虑增加轻量二次验证。

例如：

- 图像长宽比。
- 方向。
- 缩放后图像差异。
- 简单的像素比较。
- 其他成熟相似度指标。

是否引入 SSIM 等指标，由实际开发成本、依赖和性能测试决定。

不强制引入复杂算法。

但应尽可能降低明显误判。

# 八、裁剪、旋转与编辑版本

这部分需要合理控制范围。

### 旋转

对于 EXIF Orientation 引起的显示方向差异，L1 应采用一致的方向规范化规则。

对于实际改变图像像素排列的旋转，L2 可以考虑有限的方向变换比较。

但要控制额外计算成本。

### 缩放

应能够识别部分分辨率不同、视觉内容相同的照片。

例如：

```text
4032 × 3024
2016 × 1512
```

不能简单因为尺寸不同就排除视觉相似关系。

### JPEG 压缩

应该识别同一图片经过不同压缩率保存后的视觉近似。

这是本阶段的重要测试场景。

### 裁剪

裁剪会改变图像构图。

普通 pHash 对较大幅度裁剪不一定可靠。

本阶段可以对轻微裁剪进行探索性测试。

对于复杂裁剪：

**允许暂时不支持。**

不需要为了识别大幅裁剪而立即安装大型视觉模型。

### 调色与滤镜

轻微亮度、对比度变化可以纳入测试。

复杂滤镜、重绘或内容修改不要求保证识别成功。

### 文字覆盖

例如截图加水印、字幕、表情贴纸。

可以作为测试案例，但不要求全部识别。

### 本阶段边界

不要为了覆盖所有视觉变化，导致开发复杂度失控。

优先保证：

1. 不同编码。
2. 不同压缩率。
3. 不同分辨率。
4. 方向差异。
5. 轻微颜色变化。

这些基本场景可靠后，再评估复杂裁剪及编辑版本。

# 九、图像关系的数据模型

Phase 2 已经拥有 SHA-256 完全重复组。

Phase 3 需要进一步建立图像内容关系。

建议区分：

### Binary Duplicate

二进制完全相同。

依据：

完整文件 SHA-256。

### Pixel Equivalent

按照指定规范化规则，解码像素完全相同。

依据：

完整规范化像素哈希。

### Visual Similarity Candidate

视觉相似候选。

依据：

感知哈希及相关验证结果。

### Related Asset

可能属于同一个媒体资产。

例如 Live Photo 图片与 MOV 配套候选。

这不是重复文件关系。

### 重要设计要求

**不要把这些关系直接合并成一个“重复照片”布尔值。**

它们具有不同的证据强度。

数据库应能够记录：

- 关系类型。
- 涉及的文件身份。
- 算法。
- 算法版本。
- 参数。
- 原始指纹。
- 距离。
- 验证状态。
- 证据来源。
- 创建时间。
- 失效状态。

关系应当支持重新计算。

如果文件内容发生变化，旧关系不能继续作为当前有效结论。

### 避免错误传递

特别注意视觉相似关系不一定具有传递性。

例如：

A 与 B 相似。

B 与 C 相似。

但 A 与 C 可能已经差异很大。

因此：

**不能简单使用并查集，把所有视觉相似关系无条件合并为一个完全相同的照片组。**

对于 L2，建议优先保存成对候选关系。

可以生成方便审核的候选集合，但必须保留原始关系和距离，避免错误的链式合并。

L0/L1 的完全一致关系可以采用更严格的等价分组方式。

# 十、复用 Phase 2 结果，减少重复 I/O

本阶段可能需要读取和解码照片。

相比 Phase 2 的 SHA-256，资源消耗可能更高。

因此必须建立清晰的复用策略。

### 首先检查已有 SHA-256

如果两个文件已经具有当前有效且相同的完整 SHA-256：

它们不需要为了证明内容完全一致而分别重新解码。

可以复用完全重复结论。

如果需要为该组建立视觉指纹，可以选择其中一份代表文件进行计算，并在证据允许的条件下关联同组成员。

### 像素指纹缓存

对于已经完成 L1 的文件：

如果文件状态、缓存有效条件及规范化算法版本均未变化，可以复用。

### 感知哈希缓存

对于已经完成 L2 指纹计算的文件：

如果文件状态及算法配置未变化，可以复用。

### 缓存失效

以下情况应触发重新验证或失效：

- 文件大小变化。
- 文件修改时间变化。
- 已知文件身份变化。
- 解码规范化规则变化。
- 算法版本变化。
- 影响指纹的参数变化。

文件状态未变化不保证内容绝对未变化。

必须继续保留 Phase 2 已有的缓存局限说明。

可以提供明确的强制重新分析选项，但强制操作不得绕过本轮真实样本授权。

# 十一、候选搜索与规模控制

本阶段需要为未来的大型照片库考虑效率。

但不要提前建设复杂的分布式搜索系统。

### 小规模测试

对于几十至一百张图片，直接计算感知哈希距离通常可以接受。

### 未来大规模数据

如果将来索引达到数万甚至数十万张照片，所有图片两两比较会带来较高计算成本。

因此数据模型应允许未来采用：

- 哈希前缀分桶。
- 汉明距离索引。
- BK-tree。
- 其他成熟候选检索方案。

本阶段不要求立即实现复杂索引。

但不要把全库两两比较设计为未来唯一可行的方案。

### 重要区分

文件读取成本与指纹比较成本不同。

感知哈希生成通常需要读取和解码照片。

而已经持久化的感知哈希之间进行距离比较，不需要重新读取原始照片。

所以未来应尽量采用：

**一次读取 → 保存指纹 → 多次本地比较。**

不要每次调整相似度阈值，都重新下载并解码照片。

# 十三、Mac 内存、CPU 和图像解码保护

用户使用的是：

**M1 MacBook Air，8GB RAM。**

Phase 3 要特别关注图像解码产生的内存开销。

一张文件大小为 5MB 的压缩照片，解码后可能占用几十 MB 甚至更多内存。

因此：

**不能用照片文件大小直接推断解码内存需求。**

### 必须具备的保护

- 限制单文件最大像素数。
- 限制单文件处理时间。
- 限制同时解码数量。
- 防止解压缩炸弹。
- 对损坏文件安全退出。
- 避免大量图像同时驻留内存。
- 处理完成后及时释放资源。
- 不自动生成全库缩略图缓存。

建议默认单进程、低并发。

并发是否增加，依据实测结果决定。

如果遇到特别大的全景照片、超高分辨率图片或异常容器，应允许跳过并记录。

### 进程隔离

图像解码器可能出现崩溃、卡死或异常内存占用。

可以考虑复用 Phase 1/2 的受控工作进程机制。

在合理成本内，使单个图片解码失败不会导致整个任务失去已完成进度。

不要依赖无法可靠中断的单纯线程超时来宣称具备完整的解码隔离能力。

# 十五、本地测试数据

为了验证算法正例，允许使用本地合成图片和变体。

这部分不占用 NAS 真实样本数量。

建议构建标准测试集。

### 测试 A：相同文件

完全复制一张图片。

预期：

Phase 2 能识别完全重复。

Phase 3 不需要进行不必要的重复解码。

### 测试 B：不同元数据，相同像素

对同一张图片生成仅元数据不同的版本。

预期：

完整文件 SHA-256 不同。

规范化像素相同。

### 测试 C：重新压缩

同一张图片使用不同 JPEG 质量保存。

预期：

能够成为视觉相似候选。

### 测试 D：不同分辨率

对图片进行缩小或放大。

预期：

基础视觉相似检测能够合理识别。

### 测试 E：不同格式

例如 PNG 与 JPEG。

预期：

如果视觉内容保持接近，应能够形成候选。

### 测试 F：EXIF Orientation

创建不同方向元数据的测试文件。

预期：

规范化规则明确，结果可复现。

### 测试 G：轻微亮度变化

预期：

算法应具有一定容忍度。

### 测试 H：轻微裁剪

验证感知哈希的实际能力边界。

不强制要求成功。

### 测试 I：较大幅度裁剪

记录当前算法能否识别。

允许不支持。

### 测试 J：相似但不同的照片

例如同一场景的两次拍摄。

预期：

不应被标记为像素完全相同。

即使感知哈希接近，也只能作为视觉候选。

### 测试 K：纯色或简单图案

检查感知哈希是否容易产生误判。

### 测试 L：连拍照片

检查高度相似但实际上不同的图片。

### 测试 M：损坏图片

预期：

记录错误，不崩溃，不生成有效指纹。

### 测试 N：超大尺寸图片

验证解码资源限制。

### 测试 O：进程强制终止

验证已完成指纹和任务状态能够恢复。

### 测试 P：文件内容变化

验证旧指纹和旧相似关系失效。

### 测试 Q：缓存复用

重复运行时不应重新读取未变化且缓存有效的图片。

### 测试 R：阈值调整

仅修改相似度阈值时，应优先复用现有感知哈希，而不是重新解码原图。

### 测试 S：来源路径变化

验证 LAN/Tailscale 挂载切换不会导致重复文件身份。

### 测试 T：旧功能回归

Phase 1/2 原有测试仍然通过。

允许增加其他有实际价值的测试。

但不要为了增加测试数量而制造形式化测试。

## 我的补充判断

这次 Phase 3 是整个项目中比较关键的一次升级。

前两阶段主要分析文件本身，而这一阶段开始分析**图像所表达的内容**。

不过，我认为你需要特别注意三个技术问题。

**第一，感知哈希不是万能的。** pHash、dHash 在缩放、重新压缩等场景通常比较有用，但面对大幅裁剪、局部编辑或完全不同却构图相近的照片时，会存在明显局限。因此，我在交接中要求把视觉相似保存为候选关系，而不是直接合并成重复组。

**第二，真正可能拖慢系统的是图像解码，而不仅是指纹计算。** 你的 M1 MacBook Air 只有 8GB 内存。面对高分辨率 HEIC、PNG 或异常图片时，解码成本可能远高于计算一个 64-bit 感知哈希。因此，成熟解码器、像素限制、进程隔离和缓存机制比追求复杂算法更重要。

**第三，Phase 3 的结果会直接影响 Phase 4 的价值。** 你最初希望解决的，是数据恢复后某张照片文件时间异常、EXIF 缺失，但另一份备份仍然保留完整信息的情况。只有先识别出不同文件之间的视觉对应关系，后面才有可能建立可靠的版本比较与元数据恢复建议。

我建议这次继续使用 **GPT Work 的高推理强度**，但把主要工作量放在代码实现、测试和误判控制上，而不是复杂模型研究。

最终理想结果是：**一套能在 Mac 上独立运行、无需持续调用 AI、可以逐步处理大量 NAS 照片的视觉索引引擎。**
