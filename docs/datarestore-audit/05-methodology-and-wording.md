# 05 方法论、隔离原则与措辞纪律

## 5.1 核心定位

> 本项目**不是**"尽可能多地自动删除"，
> 而是**把检索能力发展为有实际证据支持的版本判定系统**。

区别在于：
- 前者以"清理量"为成功指标 → 会倾向于放宽阈值
- 后者以"判断可辩护"为成功指标 → 会倾向于收紧阈值并保留证据

## 5.2 三级判定体系

| 层 | 判据 | 可否作为证据 |
|---|---|---|
| **L0** | 全文件 SHA-256 相同 | ✅ 字节级相同，可作为证据 |
| **L1** | 解码后像素相同 | ✅ 内容相同，可作为证据 |
| **L2** | 感知哈希距离在阈值内 | ❌ **仅候选**，永不作证据 |

**L2 的正确用途**：从百万级数据里筛出几百个候选，再交给 L0/L1 验证。

实测依据见 [04-matching-metrics.md](04-matching-metrics.md)：
`d ≥ 5` 的 L2 匹配误报率 **100%**。

## 5.3 硬性安全约束（全程遵守）

1. **禁止修改、移动、覆盖、删除任何原始照片**
2. **禁止修改正式数据库**
3. **禁止启动跨国同步**
4. **禁止写回 EXIF**
5. **禁止上传私密媒体或 NAS 凭据**

### 实现方式

| 约束 | 技术手段 |
|---|---|
| 源文件只读 | 全部用 `"rb"` 打开，不调用任何写接口 |
| 恢复对象隔离 | 写入独立目录，不进共享库 |
| 不落本地盘 | 远端 `tar -cf -` 管道进 `tarfile.open(mode="r|")` 流式处理 |
| 单实例互斥 | `fcntl.flock(LOCK_EX|LOCK_NB)` + `os.execvp`，内核在进程退出时释放 |

### 单实例锁的坑

曾用 `mkdir` 做锁：

```bash
mkdir "$LOCK" || exit 1
trap 'rmdir "$LOCK"' EXIT
exit 0            # ← 拿锁后立即退出，trap 把锁删掉
```

**锁从未覆盖任何工作。** 两个实例可以同时跑。

正确做法是用内核 `flock`：

```python
fd = os.open(lockpath, os.O_CREAT | os.O_RDWR)
fcntl.flock(fd, fcntl.LOCK_EX | fcntl.LOCK_NB)   # 失败抛 BlockingIOError
os.set_inheritable(fd, True)
os.execvp(cmd[0], cmd)                            # 进程退出时内核自动释放
```

验收：

```
实例 1: 正常启动
实例 2: Active job holds <lock>   exit=75
```

## 5.4 隔离原则

| 内容 | 位置 | 是否进版本库 |
|---|---|---|
| 源代码、测试、文档 | 仓库 | ✅ |
| 审计结论摘要（本目录） | 仓库 | ✅ |
| 机器数据（JSONL、SQLite） | 本地研究区 | ❌ |
| 恢复出的媒体对象 | 远端隔离目录 | ❌ |
| 逐路径清单（含真实文件名） | 本地研究区 | ❌ |

**原因**：
1. 体积（研究区约 3.1 GB，GitHub 单仓库建议 <1 GB）
2. 隐私（含真实照片文件名、内网地址、个人路径）

本目录只发布**方法论、聚合数字、缺陷复盘**，不含任何真实文件名或内网地址。

## 5.5 措辞纪律（硬性）

| 禁止 | 必须改为 |
|---|---|
| ❌ 垃圾数据 | **尾部附加数据（未分类）** |
| ❌ 已证明无照片 | **未识别** |
| ❌ 独有照片 | **在指定参考池和阈值内未找到候选** |
| ❌ 重复文件（基于 pHash） | **感知哈希候选** |
| ❌ 可安全删除 | （禁止出现，删除决策不在本项目范围） |
| ❌ 完成（无证据） | **完成 + 命令 + 输出 + 数量 + 分母** |

### 为什么这么严格

因为措辞会反向影响判断。

例：把 42.63 GB 的尾部数据叫"垃圾数据"，
下一步就会有人问"能不能删"。而叫"未分类数据"，
下一步会问"还能识别出什么"。**这两个方向完全不同。**

### "完成"的定义

任何"完成"声明必须能回答四个问题：

1. 用什么命令？
2. 输出是什么？
3. 数量多少？
4. 分母是多少？

例：

> 对账完成。`reconcile_multisource.py` 输出：
> 成功 19,910 + 失败 3 + 缺失 28,759 = 48,672，与输入一致。

没有这四要素的"完成"一律视为未完成。

## 5.6 抽样与外推的边界

| 可以做 | 不可以做 |
|---|---|
| 抽样估算**漏检率** | 用抽样结果当**最终交付数字** |
| 抽样估算**占比** | 用 444 条样本外推**全量比例** |
| 分层抽样做**质量验证** | 用抽样结论声明"已全部验证" |

**本次教训**：凭 444 条 HEIC 样本推出"约 2% 漏选"，
实际全量 16,863 条实测是 **97.6%**。
两者差 48 倍。

## 5.7 恒等式校验

每个统计口径都必须写出并校验恒等式：

```
PNG : 导出 12,080 + 跳过 33,283 = 完整流 45,363          ✓
PNG : 唯一  8,836 + 折叠  3,244 = 导出 12,080            ✓
PNG : 完整 45,363 + 损坏 2,156 = 签名命中 47,519         ✓
对账: 成功 19,910 + 失败 3 + 缺失 28,759 = 48,672        ✓
```

**恒等式不成立时，不要继续往下算，先查账。**

本次审计中，缺陷 1（抽样漏检）和缺陷 5（PNG 尺寸）
都是通过"数字对不上"发现的，而不是通过读代码发现的。

## 5.8 三个角色的分工

| 角色 | 职责 |
|---|---|
| 主工程 | 技术上最终负责、权威数据库、最终验收 |
| 视觉算法/数据恢复 | 匹配算法、格式解析、损坏文件结构分析、恢复 |
| 审查/QA | 版本库操作、独立审计、发布 |

**关键原则**：谁写的代码谁不验收。
本次发现的 7 个缺陷中，凡是自己写自己验的部分，
平均要 3–4 轮才能发现（因为"看起来能跑"）。
