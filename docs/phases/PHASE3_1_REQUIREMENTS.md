# 六、RSS 偶发失败的诊断方向

请先从证据出发，判断问题属于哪一类。

以下是可能的方向，不代表已经确认原因。

## 6.1 测试数据的实际内存驻留

检查测试是否真正产生超过阈值的 RSS。

特别注意：

- Python 内存分配行为。
- 全零内存与实际物理页提交。
- 写时分配。
- 内存对象生命周期。
- 对象是否被提前释放。
- 测试完成前是否仍保持内存驻留。

例如，申请一个大对象，不必然意味着对应内存页已经全部驻留。

不能仅凭对象声明大小就认为 RSS 一定达到同样数值。

如果测试需要稳定触发内存限制，应确保测试对象实际访问了相应内存页，并在必要时持续保持驻留。

但不要人为修改生产代码来配合测试。

## 6.2 RSS 采样时序

检查：

- worker 启动时间。
- RSS 监控启动时间。
- 第一次采样时间。
- 采样间隔。
- 测试分配内存的时间。
- worker 释放内存或退出的时间。
- 触发终止的判断时间。

需要特别考虑：

**如果工作进程短时间内出现内存峰值，又在下一次采样前结束，轮询式 RSS 监控可能没有观察到峰值。**

这可能是测试竞争，也可能暴露生产保护机制的实际监控盲区。

必须区分两者。

不要仅通过把采样间隔设得极短来掩盖问题。

如果需要调整监控策略，应解释性能开销及仍然存在的限制。

## 6.3 测试与监控进程同步

检查测试是否存在：

- worker 尚未开始分配内存，测试就开始等待结果。
- worker 已完成任务，监控才开始采样。
- 内存峰值出现前后缺少明确同步。
- 依赖固定 sleep 时间导致偶发竞争。

如果测试需要可靠地验证内存保护，可以考虑采用明确的同步机制。

例如：

1. 启动独立 worker。
2. 确认监控已经就绪。
3. 通知 worker 执行受控内存分配。
4. worker 实际触碰目标内存页。
5. 保持该内存分配一段受控时间。
6. 验证监控观察到超限。
7. 验证仅目标 worker 被终止。
8. 验证退出原因和清理结果。

具体实现应根据现有工程选择，不强制引入某个同步框架。

**不要把固定等待时间当作可靠同步的唯一依据。**

## 6.4 进程终止结果

检查当 RSS 超限时：

- 是否确实向正确的 worker 发出终止信号。
- 是否可能发生 PID 识别错误。
- 是否存在进程已经结束的竞争条件。
- 是否正常回收子进程。
- 是否遗留孤儿进程。
- 是否影响其他无关进程。

特别注意 macOS 与 Python multiprocessing / subprocess 的实际行为。

不得直接假设 Linux 的所有进程管理行为在 macOS 上完全一致。

## 我对这次任务的额外建议

有一个技术细节值得特别指出。

你现在的内存保护方案使用的是 **RSS 轮询监控**。这种方式可以发现持续性的内存超限，但它不是操作系统级别的严格内存限制。

例如：

一个 worker 在 100 毫秒内突然分配大量内存，又迅速释放。

如果监控每 200 毫秒采样一次，就可能完全错过这次峰值。

即便单元测试全部通过，也不能因此证明监控器能够捕捉所有瞬时内存峰值。

不过，对于你这台 **8GB M1 MacBook Air**，现阶段我不建议为了追求绝对隔离而立即引入虚拟机、Docker 或复杂的进程沙盒。

更合理的工程优先级是：

**先确认现有机制没有明显缺陷，再通过图像像素上限、预估内存占用、低并发和独立 worker，共同控制实际风险。**

另外，这次维护不需要继续读取 NAS 的 28 个样本。测试全部可以在 Mac 本地完成。

**我的建议是：把 Phase 3.1 作为一次独立的小型维护任务执行，完成后再进入 Phase 4。** 不要把两个阶段合并成长时间任务，这样更容易区分稳定性修复与新增功能造成的问题。
